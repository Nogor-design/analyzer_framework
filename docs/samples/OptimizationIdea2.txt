Example 1:
I want the best PF for every 4-hour time slice of the day, with Reverse false and Reverse true.

That means:

DurationTimeH:

Each template would then optimize the remaining internal parameters.

Core design concept:
Parameters need roles, not just fixed/optimized.

Add support for parameter roles such as:

1. fixed
   - Same value in every generated template.

2. matrix_axis
   - Expands into separate templates.
   - Example: StartTimeH, Reverse, averageSlow.

3. optimize_inside_template
   - NinjaTrader sweeps this inside each generated XML.
   - Example: averageFast, MaxStop, MaxTPRatio.

4. inherited_from_parent_result
   - Later stage receives this value from a selected parent optimizer row.

5. refine_around_parent_result
   - Later stage creates a tighter range around the parent winner.
   - Example: winner averageFast ± 5 step 1.

6. validation_only
   - Used only for final fixed Backtest validation or review.

This needs to be dynamic for any NinjaTrader strategy.
Do not hardcode Pantheon-only parameters as the system design.
The UI may show Pantheon examples, but the engine should derive strategy parameters from the selected seed XML/session parameter catalog.

Important correction to workflow:

The Recipe/Matrix optimizer should support autonomous execution.

Do NOT design this as a manual-only flow where the user must click:
1. Generate XMLs
2. Run on NinjaTrader
3. Refresh results
4. Pick winners
5. Generate next stage

Instead, the intended workflow is:

1. User configures the full recipe.
2. User defines selection rules, guardrails, target candidate count, max runtime/combination limits, and stop conditions.
3. User starts the recipe run.
4. System generates stage templates.
5. System runs the generated templates through the existing NinjaTrader AddOn workflow.
6. System monitors NinjaTrader status/output.
7. System ingests completed results.
8. System applies the user-defined selection rules.
9. System saves selected candidates and lineage.
10. System generates the next child-stage templates.
11. System runs the next child stage automatically.
12. System repeats until the recipe reaches final fixed Backtest validation or a configured stop condition.

This should be an autonomous loop, not a wizard that requires user clicks between every stage.

The user should still be able to inspect, pause, resume, rerun, clone, or override any stage after the fact.

Add an orchestration layer.

Suggested concept:

RecipeRunOrchestrator

Responsibilities:
- Load session.json and recipe.json.
- Build or load recipe_plan.json.
- Determine current recipe state.
- Generate templates for the current stage if needed.
- Submit the current stage to the existing NinjaTrader AddOn.
- Monitor run status through the existing command/status files and output folders.
- Detect completed result files.
- Ingest results using the existing optimizer result parser.
- Apply stage-specific selection rules.
- Persist selected rows and lineage.
- Generate the next stage from selected parent rows.
- Continue automatically until complete, failed, paused, or stopped.

The orchestrator should be resumable.

If the app restarts, the system should be able to inspect the saved session folder and determine:

- recipe not started
- stage templates generated
- stage running
- stage completed but results not ingested
- stage results ingested
- stage selection completed
- next child stage generated
- final validation needed
- recipe complete
- recipe failed
- recipe paused
- recipe stopped by user
