Core idea:

Most AI systems only store documents, notes, embeddings, chats, or files in a vector database. That helps with retrieval, but it does not tell the AI:

- What is currently true
- Which information is active vs historical
- Where a fact or decision came from
- Which version of a strategy, agent, workflow, or config is approved
- What changed over time
- What evidence supports a decision
- Whether a change improved or harmed performance
- How to roll back to a previous known-good version
- Whether the system is actually improving

I want the system to manage reality over time, not just remember text.

Purpose:
Find relevant information, but do not treat retrieved information as automatically true.

C. State Management Layer

This is the active truth layer.

It should track current state for things like:

- Active projects
- Active strategies
- Active strategy versions
- Approved strategy versions
- Current testing phase
- Current deployment status
- Current risk settings
- Current account rules
- Current prop-firm constraints
- Current market/session settings
- Current agent permissions
- Current workflow status

Example trading state:

Strategy:
- Name: LondonBreakout
- Active version: v12
- Last approved live version: v10
- Current phase: forward testing
- Instrument: NQ
- Session: 00:00 to 07:00 America/Denver
- Max stop: 100 ticks
- Max daily loss: 750
- Prop firm trailing drawdown limit: 1500
- Approved for live PA: false
- Approved for evaluation accounts: true

The key point:
The system must clearly distinguish active truth from historical notes.

D. Provenance Layer

Every important claim, rule, decision, result, or state change should have traceable provenance.

Track:

- Source type
- Source file
- Source path
- Source system
- Source date
- Created by human or AI
- Generated by which agent/model/tool
- Related commit hash, if available
- Related backtest file
- Related dataset
- Related NinjaTrader version/config, if relevant
- Confidence level
- Verification status
- Approval status
- Human reviewer, if any

Example:

Claim:
"LondonBreakout_v12 performs better with ATR trailing enabled."

Provenance:
- Source: NinjaTrader Strategy Analyzer CSV
- File: reports/LondonBreakout_v12_NQ_2026-05-01.csv
- Data period: 2022-01-01 to 2026-04-30
- Generated by: NinjaTrader 8
- Generated at: 2026-05-01
- Strategy code commit: abc123
- Status: needs forward testing
- Confidence: medium
- Approved for live: false

F. Rollback / Versioning Layer

The system should support rollback of:

- Strategy versions
- Configurations
- Agent prompts
- Workflow definitions
- Risk settings
- State changes
- Generated code
- Research decisions where appropriate

Rollback should not erase history.

It should:

- Restore a previous known-good state
- Preserve the rejected or failed version
- Record why rollback happened
- Link to the evaluation that triggered rollback
- Create follow-up learning notes

Example:

Rollback:
- From: LondonBreakout_v14
- To: LondonBreakout_v13
- Reason: v14 failed forward test
- Evidence: forward_test_report_2026-05-10.csv
- Learning: volatility filter reduced trade frequency but increased average adverse excursion
- Next action: retest filter only during NY session

The system needs scoreboards and evaluation harnesses.

For trading strategies, track:

- Net profit
- Profit factor
- Max drawdown
- Sharpe ratio
- Sortino ratio
- Win rate
- Average trade
- Number of trades
- Long/short performance
- Time-of-day performance
- Session performance
- Market regime performance
- Slippage sensitivity
- Commission sensitivity
- Monte Carlo pass probability
- Risk of ruin
- Prop firm rule compliance
- Backtest vs forward-test degradation
- Live vs sim difference
- Daily loss violations
- Trailing drawdown violations

For coding agents, track:

- Compile success
- Test pass rate
- Lint status
- Regression count
- Runtime errors
- Code complexity change
- Files modified
- Human review outcome
- Whether changes followed project conventions

For business/workflow agents, track:

- Time saved
- Error reduction
- Cost per completed workflow
- Manual review rate
- Customer response time
- Conversion rate improvement
- Failed automation count

The AI should not only generate outputs. It should be judged by outcomes.

H. Policy / Permission Layer

The system should define what agents are allowed to do.

Examples:

- AI can propose strategy changes but cannot approve live deployment.
- AI can run backtests but cannot trade live.
- AI can mark a strategy as candidate but not production.
- AI can modify code in a feature branch only.
- AI can recommend risk setting changes but requires human approval.
- AI can roll back sim/testing versions automatically but not live production systems.
- AI must require approval before changing prop-firm account settings.

8. Important Design Principles

Use these principles:

- Do not let vector search define truth.
- Separate historical memory from active state.
- Make important changes event-driven and auditable.
- Preserve failed experiments instead of deleting them.
- Every claim should link to evidence.
- Every evaluation should link to artifacts and configuration.
- Every approval should identify who approved what and when.
- Every rollback should explain why it happened.
- Prefer deterministic workflows for critical decisions.
- Use AI for reasoning and synthesis, not blind authority.
- Make the system useful before making it complex.
- Keep the design modular so it can support trading, coding, and business workflows later.
